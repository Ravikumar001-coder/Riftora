# GameVerse - Agent Instructions & Architecture Guidelines (AGENTS.md)

Welcome, AI Agent. This document contains the definitive architectural rules, technology constraints, and implementation guidelines for the **GameVerse Esports Tournament Management System (ETMS)**. 

**Read and strictly adhere to these rules before modifying any code.**

---

## 1. Project Overview & Vision
**GameVerse** is a B2B2C SaaS platform designed for professional esports tournament organization, team/player management, live scoring, and broadcast integration.
It replaces disjointed tools (Discord + Google Sheets) with a unified, real-time command center.

### Core Ecosystem Portals
The platform is strictly divided into four distinct portals (ecosystem sides):
1. **Admin / Tournament Organizer Panel**: B2B command center for creating tournaments, managing operations, and resolving disputes.
2. **Player & Team Portal**: B2C dashboard for players to manage rosters, register for events, check in, and view match credentials.
3. **Public Live Tournament Website**: Public-facing discovery and live leaderboard tracking for fans.
4. **Production & Stream Control Panel**: Dedicated overlay controls and scene management for live broadcast teams.

## 2. Technology Stack & Restrictions

> **CRITICAL RULE**: The frontend uses **JavaScript (.js/.jsx) ONLY**. Do NOT generate or use TypeScript (.ts/.tsx).

### Frontend (gameverse-frontend)
- **Framework**: React 19 (Single Page Application)
- **Build Tool**: Vite
- **Language**: JavaScript (ES6+)
- **Routing**: React Router v7
- **Server State**: TanStack Query v5 (REST API data fetching & caching)
- **Global/Local State**: Zustand
- **Styling**: Tailwind CSS v3 + shadcn/ui
- **Forms**: React Hook Form + Zod (Validation)
- **Real-Time**: `@stomp/stompjs` + `sockjs-client`

### Backend (gameverse-backend)
- **Architecture**: Modular Monolith (packaged by feature, not layers)
- **Framework**: Java 21 (LTS) + Spring Boot 3.3.x
- **API Style**: RESTful JSON API via Spring MVC
- **Database**: MYSQL
- **ORM**: Spring Data JPA + Hibernate 6
- **Migrations**: Flyway
- **Security**: Spring Security 6 (Stateless JWT)
- **Real-Time**: Spring WebSocket + STOMP Protocol
- **Validation**: Jakarta Validation 3 (Hibernate Validator)

## 3. Architecture & Folder Structure

### Frontend Structure
The frontend architecture enforces a strict separation between **Portals** (page routes) and **Features** (business logic/components).

- `src/portals/{admin|player|public|production}/`: Contains layouts, pages, and route configurations specific to that portal. Pages should act primarily as composers.
- `src/features/{auth|tournaments|matches|etc}/`: Encapsulates domain-specific logic. Contains API calls, domain components, and domain state.
- `src/components/`: Only for highly reusable, domain-agnostic UI elements (e.g., `ui/` for shadcn, `common/`, `feedback/`).
- Do not cross-contaminate portal layouts. The Admin portal components should not leak into the Public portal.

### Backend Structure
The backend is a **Modular Monolith**. Avoid monolithic "Service" or "Controller" packages.
- `src/main/java/com/gameverse/core/`: Global concerns (Security, Exceptions, WebSocket config).
- `src/main/java/com/gameverse/modules/{domain}/`: Domain boundaries (e.g., `auth`, `organization`, `match`). Each module contains its own `controller`, `service`, `model`, `repository`, and `dto` packages.
- Modules should interact via Services, not by directly calling another module's repository.

## 4. Coding Conventions & Implementation Rules

### Frontend Rules
1. **API Integration**: All API fetching MUST use `TanStack Query` (`useQuery`, `useMutation`). Do not use `useEffect` for data fetching. Axios is only used as the fetcher function inside React Query.
2. **State Management**: Use `Zustand` for global UI state, WebSocket connections, and Auth state. Use `TanStack Query` for server state.
3. **Styling**: Use Tailwind utility classes. For conditional classes, use `clsx` and `twMerge` (standard shadcn/ui `cn` utility).
4. **Forms**: Use `React Hook Form` integrated with `Zod` resolvers.
5. **Real-time**: WebSocket connections (STOMP) are managed globally via a Zustand store (`stompStore.js`). Components should subscribe to specific topics via custom hooks (e.g., `useLeaderboard.js`).

### Backend Rules
1. **Primary Keys**: Use `UUID` generated by the application for all entities.
2. **Soft Deletes**: Implement soft deletes (`is_deleted`, `deleted_at`) rather than hard database deletes.
3. **Transactions**: Apply `@Transactional` at the `@Service` layer, never at the `@Controller` layer. Use `@Transactional(readOnly = true)` for pure fetch operations.
4. **N+1 Problem Prevention**: Use `@EntityGraph` or `JOIN FETCH` for fetching related entities. Default all `@OneToMany` to `LAZY`.
5. **DTO Mapping**: Never expose JPA entities directly to the API. Always map to DTOs.
6. **Stateless APIs**: The API must remain 100% stateless. Session data must only exist within the JWT token.

## 5. Security & Authentication (RBAC)

- **Authentication**: Handled via short-lived JWT Access Tokens (passed via `Authorization: Bearer <token>`) and long-lived HttpOnly Refresh Tokens.
- **Frontend Routing Guards**: Use `AuthGuard` to protect private routes and `RoleGuard` to restrict views based on the user's current organization role.
- **Backend Authorization**: Secure endpoints using `@PreAuthorize` based on roles and claims. Ensure multi-tenant safety by validating that the requested resource (e.g., Tournament) belongs to the Organization the user has rights to.

## 6. UI/UX Guidelines
- **Aesthetic**: Deep navy backgrounds (`#071426`), vibrant accents (e.g., blue `#2563EB`, red `#EF4444` for LIVE status).
- **Layout**: Follow the 3-level navigation pattern for internal portals (Global Icon Nav -> Context Sidebar -> Top Header -> Main Content).
- **Data Presentation**: Use "Bento Box" grids for dashboards. Real-time data (like leaderboards or live operations) must prioritize high-contrast visibility and immediate visual feedback without page reloads.

## 7. Implementation Workflow

When building new features, follow the sequential phases defined in `Phases & Tasks.md`:
1. **Foundation Layer** (Auth, Org, Game Config)
2. **Participant Layer** (Teams, Tournaments)
3. **Operations Layer** (Registration, Scheduling)
4. **Match Day Layer** (Credentials, Live Ops, Scoring)
5. **Live Data Layer** (Leaderboard, Stats)
6. **Broadcast Layer** (Overlays, Stream Control)
7. **Support Layer** (Chat, Notifications, Payments)

**Before writing code**:
1. Identify which ecosystem portal the feature belongs to.
2. Identify which domain feature folder it maps to.
3. Ensure the backend module is created before wiring the frontend API.

## 8. Common Mistakes to Avoid
- **Using TypeScript**: The project has explicitly shifted to JavaScript. Do not generate `.ts` or `.tsx` files.
- **Direct Fetching**: Using `axios.get()` directly in a React component instead of wrapping it in `useQuery`.
- **Hard Deletes**: Writing `repository.delete()` instead of updating a `deleted_at` flag.
- **God Services**: Putting all backend logic into a single service. Keep logic confined to its specific module.
- **Mixing Portals**: Adding Admin features into the Player portal layout. Keep the 4 ecosystems strictly isolated in routing.
